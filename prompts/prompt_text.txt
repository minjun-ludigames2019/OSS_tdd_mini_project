// 첫번째 프롬프트 AI 답변
현재 app.py의 combat_tick 함수 내에 있는 무기 등급(eq_rarity)에 따른 데미지 배율 계산 로직은 새로운 등급이 추가될 때마다 코드를 직접 수정해야 하므로 **개방 폐쇄 원칙(OCP, Open-Closed Principle)**을 위반하고 있습니다.

이를 리팩토링할 수 있는 객체지향적 접근 방식 또는 디자인 패턴 3가지를 제안해 드립니다.

1. 딕셔너리(Map)를 이용한 데이터 주도 매핑 (Data-Driven Mapping)
가장 간단하고 직관적인 해결책으로, 파이썬에서 흔히 사용되는 방식입니다. 조건문들을 딕셔너리에 매핑해두고, 해당 등급(key)을 기반으로 값(value)을 가져오는 형태입니다.

개념: 등급과 배율의 관계를 데이터(Dictionary)로 분리하고, 로직에서는 데이터를 조회하기만 합니다.
장점:
코드가 매우 간결해집니다.
새로운 등급이 추가되더라도 로직 코드를 변경할 필요 없이 딕셔너리에 새로운 키-값 쌍만 추가하면 됩니다.
단점:
각 등급마다 단순한 '고정 배율'이 아닌, 복잡한 로직(예: 계산식, 확률 적용 등)이 들어가야 할 경우에는 딕셔너리에 함수나 객체를 매핑해야 하므로 조금 더 복잡해질 수 있습니다.

2. 전략 패턴 (Strategy Pattern)
무기의 각 등급을 '하나의 전략'으로 바라보고 다형성을 이용해 해결하는 흔한 디자인 패턴입니다.

개념: 데미지 배율을 계산하는 인터페이스(또는 추상 클래스)를 정의하고, 각 무기 등급(일반, 희귀, 영웅 등)이 이 인터페이스를 구현하는 각각의 구체적인 전략 클래스가 됩니다.
장점:
OCP 원칙을 가장 완벽하게 지킬 수 있습니다. 새로운 등급 추가 시 기존 코드 변경 없이 새로운 전략 클래스만 생성하면 됩니다.
등급별로 데미지를 구하는 공식이나 부가 효과(예: 출혈 효과, 크리티컬 확률 분기 등) 등 복잡한 로직이 포함될 때 확장이 매우 편리합니다.
단점:
단순한 숫자 매핑에 적용하기에는 클래스를 불필요하게 많이 만들어야 하므로 오버엔지니어링(Over-engineering)이 될 위험이 있습니다.

3. Enum (열거형) 활용 패턴
파이썬의 Enum 클래스를 사용하여 각 무기 등급과 고유의 속성(여기서는 배율)을 캡슐화하는 방식입니다.

개념: 상태 상수에 단순한 숫자(0, 1, 2...) 대신 독립적인 Enum 객체를 사용하고, 각 멤버 변수에 배율 값을 할당합니다.
장점:
"마법의 숫자(Magic Number)"인 0, 1, 2의 의미(Normal, Rare, Epic 등)를 명확하게 해주어 가독성이 비약적으로 상승합니다.
관련 프로퍼티(배율값)를 Enum이 직접 관리하기 때문에 응집도가 높아집니다.
단점:
기존 데이터 구조가 단순 정수(int)로 선언되어 있다면(game_state["eq_rarity"] = 0), 이를 Enum 객체로 치환하기 위해 상태 데이터를 다루는 다른 부분들의 리팩토링이 함께 필요할 수 있습니다.

추천:
현재는 단순히 배율 값(상수)만 반환하고 있으므로 1. 딕셔너리(Map) 변환이나 3. Enum 패턴을 우선 고려하는 것이 실용적입니다. 만약 향후 무기 등급마다 '스킬 발동'이나 '특별한 연산'이 추가되어 분기마다 코드가 길어진다면 2. 전략 패턴이 가장 좋은 선택이 될 것입니다.

// 두번째 프롬프트 AI 답변
딕셔너리 매핑 방식을 적용하여 app.py의 combat_tick 함수 내 if / elif 분기문을 리팩토링했습니다.

등급과 배율을 rarity_multipliers = {0: 1, 1: 2, 2: 5, 3: 15, 4: 50} 딕셔너리로 관리하고, .get() 메서드를 통해 기본값을 1로 처리함으로써 향후 새로운 등급이 추가되더라도 딕셔너리 항목만 추가하는 방식으로 깔끔하고 확장 전개(OCP)가 용이하도록 수정했습니다.

기존의 변수 명세나 응답 결과(JSON)는 전혀 건드리지 않아 기존 테스트가 문제없이 동작하도록 유지했습니다! 추가되었습니다.
